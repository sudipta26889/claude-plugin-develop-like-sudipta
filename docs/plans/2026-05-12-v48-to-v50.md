## Phase 3 — v5.0 scaffolding: /cc-monitor command + monitor_loop.sh

**Scope:** Create the v5.0 surface area for continuous monitoring. THIS PHASE BUMPS TO v5.0-alpha.

**Files (all new):**
- `develop-like-sudipta/commands/cc-monitor.md`
- `develop-like-sudipta/commands/cc-monitor-stop.md`
- `develop-like-sudipta/skills/sd-claude-code-access/scripts/monitor_loop.sh`
- `develop-like-sudipta/skills/sd-claude-code-access/references/monitor_mode.md`
- `develop-like-sudipta/skills/sd-claude-code-access/assets/monitor_directive_template.md`

**Tasks:**

1. **`commands/cc-monitor.md`** — slash command that takes a free-form objective string + workspace and starts the monitor loop. Pattern: Cowork-readable directive; substrate detection (Path A); calls `launch_cc.sh` (auto-launch CC for the workspace if missing); calls `start_watchdog.sh`; calls `monitor_loop.sh` in background; reports to user.

2. **`commands/cc-monitor-stop.md`** — slash command that creates `<workspace>/.cc/monitor.stop` (lockfile). The loop checks for it each cycle and exits cleanly.

3. **`scripts/monitor_loop.sh`** — the outer cycle scheduler. Each cycle:
   - **OBSERVE** — dispatches subagents in parallel: Claude-in-Chrome probe (URL from `<workspace>/.cc/monitor.json` config), SSH probe via Desktop_Commander (host + log path from config).
   - **CLASSIFY** — Cowork synthesizes: "all healthy" / "anomaly: <category>".
   - **DECIDE** — if anomaly: write `.cc/bug-<auto-id>.md` and send `Read .cc/bug-<id>.md and apply bug-driven TDD` to CC. If healthy: log heartbeat, sleep.
   - **ACT** — bug-driven TDD as today; on green: trigger `/deploy` via CC directive.
   - **RECORD** — append `monitor_cycle` event to `<workspace>/.cc/monitor.jsonl` AND `~/.cache/ccbridge/learnings/<id>.jsonl` via `learning.sh`.
   - **SLEEP** — `${MONITOR_INTERVAL_S:-180}` seconds; check `.cc/monitor.stop` lockfile.

4. **`references/monitor_mode.md`** — the methodology: cycle structure, config schema (URL to probe, SSH host, log path, anomaly classifier rules, stop conditions), example monitor.json, example monitor.jsonl event.

5. **`assets/monitor_directive_template.md`** — how to phrase a monitoring objective so CC can act on it.

6. **Update `install.sh`** to include `monitor_loop.sh` in the SCRIPTS array.

7. **Update `learning.sh`** documentation (header comment only) to list `monitor_cycle` as a canonical category.

**Acceptance:**
- `bash develop-like-sudipta/skills/sd-claude-code-access/scripts/monitor_loop.sh --dry-run` runs one cycle in detect-only mode and exits 0.
- `mcp__Desktop_Commander__start_process` can launch monitor_loop.sh in background and `mcp__Desktop_Commander__force_terminate` can stop it.
- `install.sh` copies `monitor_loop.sh` into `~/.cache/ccbridge/` (verify with `ls ~/.cache/ccbridge/monitor_loop.sh`).

**Commit message:** `feat(monitor): scaffold /cc-monitor + monitor_loop.sh + references/monitor_mode.md (v5.0.0-alpha.1)`

## Phase 4 — Stop conditions + resource governance

**Scope:** Make monitor mode safe to leave running for hours/days.

**Files:**
- `develop-like-sudipta/skills/sd-claude-code-access/scripts/monitor_loop.sh` (update)

- `develop-like-sudipta/skills/sd-claude-code-access/references/monitor_mode.md` (update)

**Tasks:**

1. **`max_cycles`** — N, default unlimited; loop exits after N iterations.
2. **`max_duration_hours`** — H, default 24; loop exits when wall-clock exceeds H.
3. **`max_fix_attempts_per_cycle`** — default 3 (consistent with bug-driven TDD); after 3 consecutive failed fix-and-deploy attempts on the same anomaly category, escalate via `escalate.sh` and pause for `cooldown_minutes`.
4. **`.cc/monitor.stop` kill switch** — checked at the top of every cycle. If present, loop exits cleanly + writes a `monitor_stopped` state event.
5. **Per-cycle wall-clock cap** — `cycle_timeout_s`, default 300. If a single cycle's OBSERVE+CLASSIFY+DECIDE+ACT doesn't complete in 5 min, abort + log + continue to next cycle.

**Acceptance:**
- `monitor_loop.sh --max-cycles 2` exits after 2 cycles.
- `touch <workspace>/.cc/monitor.stop` → next cycle exits within 10s.
- Three consecutive failed fix cycles trigger `escalate.sh`.

2. **OBSERVE — SSH/prod-log path:** via `mcp__Desktop_Commander__start_process` running `ssh <host> 'tail -100 <log>'`. Capture into `.cc/monitor/cycle-<N>-logs.txt`.
3. **CLASSIFY:** Cowork reasons over the two captures. Anomaly categories: `5xx_burst`, `slow_response`, `console_error`, `network_failure`, `disk_full`, `process_down`, `unknown`. Default heuristics live in `monitor_mode.md`; project-specific overrides via `<workspace>/.cc/monitor.json`.
4. **ACT — deploy step:** if a fix lands green (verify-gate + browser-test), use the existing `/deploy` skill via a `.cc/deploy.md` directive sent to CC. Do NOT bypass `/deploy`'s discipline (pull-policy, Compose-vs-Swarm semantics — both shipped in v4.6.1+v4.6.2).

- End-to-end test: inject a known 500 into a local test server → monitor detects → bug-driven TDD writes a failing test → CC fixes → deploy step is invoked → 500 disappears → next monitor cycle reports green.

# Playwright spec generation — from test markdown to durable spec files

This reference explains how each per-phase test markdown becomes a `*.spec.ts` Playwright file. The generated specs are committed into the project so a future CI run, a different developer, or a re-run of the skill itself has the regression coverage baked in.

## File layout

```
<workspace>/
├── docs/
│   └── e2e-testing/
│       ├── phase-1-login.md
│       ├── phase-2-dashboard.md
│       ├── phase-3-checkout.md
│       ├── E2E-SUITE.md           # generated by /e2e-suite
│       ├── screenshots/
│       │   └── phase-1/
│       │       ├── s1.png
│       │       └── s2.png
│       └── specs/
│           ├── phase-1.spec.ts
│           ├── phase-2.spec.ts
│           ├── phase-3.spec.ts
│           ├── e2e.spec.ts        # umbrella, generated by /e2e-suite
│           ├── fixtures.ts        # shared fixtures (auth, baseURL)
│           └── playwright.config.ts
```

If the project already has Playwright installed elsewhere (e.g. `tests/e2e/`), reuse it — read `playwright.config.ts` and emit into the existing tests directory. Otherwise scaffold under `docs/e2e-testing/specs/` and add a `npx playwright install` directive to phase 1.

## Markdown → spec mapping

The markdown sections drive the spec verbatim:

| Markdown section | Spec output |
|---|---|
| Test ID | `test.describe` name + filename slug |
| Objective | comment block above the describe |
| Preconditions | `test.beforeAll` — env checks, fixture loads |
| Setup | `test.beforeEach` — DB seed, feature flag, navigate to start URL |
| Steps (numbered, each with action + expected) | one `test.step('s<n>: <description>', async () => { ... })` per step |
| Screenshot anchors | `await page.screenshot({ path: 'screenshots/phase-<N>/s<n>.png' })` at the end of the matching step |
| Console assertions | `page.on('console', …)` listener in `beforeEach` + final `expect(consoleErrors).toHaveLength(0)` (or whitelist) |
| Network assertions | `page.route` interceptor in `beforeEach` capturing matching requests + final `expect(...).toMatchObject(...)` |
| Result | NOT emitted — that's the markdown's runtime status, the spec's status is whatever Playwright reports |
| Notes | comment at bottom of file |

## Selector strategy

Always prefer in this order:
1. `data-testid` — most stable
2. `getByRole('button', { name: '...' })` — accessible-name based
3. `getByText('...')` — visible text
4. `locator('css-selector')` — CSS as last resort
5. XPath — never, except for legacy / iframe edge cases

> **Source-side discipline:** the directive template at
> `assets/directive_template.md` REQUIRES every interactive UI element
> to carry a stable `data-testid`. This is enforced at directive time,
> not at test time — the developer adds testids when writing the
> component, not when writing the test. Spec generation can therefore
> default to `getByTestId(...)` selectors with high confidence.

If the markdown's step references an element by visible text, emit `getByText` or `getByRole`. If the project already uses `data-testid` widely (check existing components), prefer that and recommend CC add testids as part of the directive for that phase.

## Idempotent overwrite

A spec file is regenerated only if the source markdown's `## Steps` content hash changed.

Algorithm:

```
hash = sha256(steps_section_text)
existing_spec_top_comment = "// source-hash: <hash>"
if existing_spec_top_comment matches new hash → no-op
else → overwrite, update top comment
```

This keeps the spec stable across cosmetic markdown edits (typos, reformat) but regenerates whenever the actual test steps change.

## Auth fixture

Emit once, in `specs/fixtures.ts`:

```typescript
import { test as base, expect } from '@playwright/test';
import * as fs from 'fs';
import * as path from 'path';

const STORAGE_STATE = path.join(__dirname, '..', '..', '..', '.cc', 'auth', 'storage-state.json');

export const test = base.extend({
  storageState: async ({}, use) => {
    if (fs.existsSync(STORAGE_STATE)) {
      await use(STORAGE_STATE);
    } else {
      await use(undefined);
    }
  },
});

export { expect };
```

Every per-phase spec imports from `./fixtures` instead of `@playwright/test` directly.

## Playwright config (scaffold once)

If `specs/playwright.config.ts` doesn't exist, emit:

```typescript
import { defineConfig, devices } from '@playwright/test';
import * as fs from 'fs';
import * as path from 'path';

const DEV_SERVER_URL = process.env.DEV_SERVER_URL || 'http://localhost:5173';

export default defineConfig({
  testDir: '.',
  fullyParallel: false,
  retries: process.env.CI ? 2 : 0,
  reporter: [['html', { outputFolder: '../playwright-report' }], ['list']],
  use: {
    baseURL: DEV_SERVER_URL,
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
    video: 'retain-on-failure',
  },
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
  ],
});
```

Adjust port / browser projects based on the project's existing tooling.

## Umbrella `e2e.spec.ts`

Generated by `/e2e-suite`. Pattern:

```typescript
// source: docs/e2e-testing/E2E-SUITE.md
// generated by sd-claude-code-access /e2e-suite
import './phase-1.spec';
import './phase-2.spec';
import './phase-3.spec';
// ...
```

Playwright picks up the imports and runs them as one suite. Coverage table at the top of `E2E-SUITE.md` provides the human view.

## Selector evolution

If a feature changes in a later phase (e.g. phase 3 renames a button that phase 1 tested), the per-phase test for phase 1 starts failing. Two options:

1. **Soft update** — phase 3's directive includes a note "phase-1.spec.ts step s4 selector needs update to `getByRole('button', { name: 'New Label' })`" and the post-phase loop re-runs phase 1's markdown to regenerate.
2. **Hard versioning** — keep `phase-1.spec.ts` as-is (it documents the state at phase 1) and emit `phase-3-regression-of-phase-1.spec.ts` for the updated selector.

Default to (1) for in-flight projects; use (2) only when the user explicitly wants per-phase historical snapshots.

## CI integration hint

After the run, leave a `docs/e2e-testing/RUNNING.md` with:

```markdown
# Running the browser tests

## One-time
npm install -D @playwright/test
npx playwright install --with-deps chromium

## Run all
DEV_SERVER_URL=http://localhost:5173 npx playwright test --config=docs/e2e-testing/specs/playwright.config.ts

## Run one phase
npx playwright test --config=docs/e2e-testing/specs/playwright.config.ts phase-3.spec.ts
```

This is the only docs file that explains how to USE the tests — every other md describes the tests themselves.

## Don't

- Don't emit `expect(...).toBeVisible({ timeout: 30000 })` blindly. Match the timeout to what the markdown said.
- Don't use `page.waitForTimeout` — Playwright has assertion auto-retry; rely on it.
- Don't bake URLs. Always go through `baseURL` from the config.
- Don't generate snapshot tests (`toHaveScreenshot`) unless the markdown explicitly asks for visual regression. Snapshots are flaky without curated baselines.
